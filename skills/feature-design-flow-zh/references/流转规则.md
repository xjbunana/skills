# 流转规则

## 状态纪律

设计阶段和开发阶段必须分开追踪。

推荐的设计状态：
- 待设计
- 设计中
- 待确认
- 已完成
- 需修改

推荐的开发状态：
- 设计阻塞
- 待开发
- 开发中
- 已完成
- 需修复

QA 决策状态固定为：
- 已确认
- 待确认
- 暂缓

不要因为文档已经存在，就把它标记为完成。文档需要达到 Definition of Done，并且经过用户确认。

## 流程选择

轻量流程适合单模块、小改动、低风险需求：

```text
需求文档 + QA 决策记录 -> 模块详细设计 -> 小型复查 -> 开发
```

完整流程适合多模块、高风险、长期维护或 AI 行为复杂的需求：

```text
需求文档 -> QA 决策记录 -> 拆分设计总览 -> 公共上下文
-> 模块详细设计 -> 进度门禁 -> 设计复查 -> 开发
```

当不确定时，默认走完整流程的前半段，等模块边界清楚后再决定是否降级为轻量流程。

## 确认门禁

以下节点需要用户确认：
- 需求范围冻结
- 模块边界冻结
- 关键设计文档标记完成
- 复查结论会改变范围或架构
- 从设计阶段进入开发阶段

设计文档确认后，要回查上游文档并同步矛盾，再继续推进。

## Definition of Done

需求文档完成标准：
- 背景、目标、范围、不做事项清楚。
- 至少有核心流程或典型场景。
- 验收标准可验证。
- 关键未知项已标记为待确认。

QA 决策记录完成标准：
- 每个关键问题都有结论、理由和状态。
- 状态只使用已确认、待确认、暂缓。
- 待确认项不会被当成实现依据。

拆分设计总览完成标准：
- 模块边界和依赖顺序清楚。
- 每个模块都有定位说明。
- 设计顺序和开发顺序能解释为什么这么排。

公共上下文完成标准：
- 包含所有模块共享且稳定的约定。
- 没有混入单模块独有细节。
- 新会话能据此理解项目基本规则。

模块详细设计完成标准：
- 有明确职责和依赖。
- 涉及接口时，有方法、路径、请求示例、响应示例。
- 涉及数据时，有字段、类型、必填、状态含义。
- 涉及逻辑时，主流程和至少一个异常/边界路径被覆盖。
- 涉及 AI 行为时，Prompt/Tool 触发条件、参数来源、返回处理清楚。
- 验收点能被测试或人工验证。

复查完成标准：
- AI 已主动检查范围、命名、数据、接口、模块边界、AI/Tool/Prompt、开发就绪度。
- 严重和中等问题已确认修改、暂不修改或待确认。
- 会阻塞开发的问题没有被静默跳过。

## 先设计后开发

只有满足以下条件，才进入开发：
- 需求已整理
- 关键 QA 决策已记录
- 必要的设计总览或轻量模块设计已存在
- 公共上下文在完整流程中已存在
- 必要模块设计已完成
- 设计复查已完成
- 严重和中等问题已修复或明确暂缓

如果用户明确要求跳过设计直接开发，可以服从用户，但应把发现的假设用轻量方式记录下来。

## 变更处理

需求中途变化时：
- 更新需求文档
- 增补或更新 QA 决策
- 检查模块顺序和依赖是否变化
- 更新受影响的模块文档
- 如果变化造成不一致，记录到复查问题中

不要在范围变化后静默更新进度状态。
