# 文档职责

用这份说明来判断内容应该放在哪个文档里，避免一个文档承担太多职责。

## 需求文档

作用：定义功能为什么要做、做什么、不做什么。

建议包含：
- 背景和目标
- 本期范围
- 不做事项
- 核心用户流程
- 功能清单
- 数据和接口预期
- 验收标准
- 后续扩展

避免：
- 放太深的代码实现细节
- 把未确认的判断写成确定结论

完成标准：需求读完后，应能回答“为什么做、给谁用、做到什么程度、什么明确不做、怎么验收”。

## QA 决策记录

作用：保存需求讨论中的关键问题、取舍和结论。

建议包含：
- 问题
- 结论
- 理由或权衡
- 状态：已确认、待确认、暂缓
- 对应日期或版本

状态值域固定为：
- 已确认：已形成设计依据
- 待确认：继续推进前需要用户判断
- 暂缓：当前阶段不处理，但保留记录

这个文档用于避免后续会话反复追问同一个问题。

## 拆分设计总览

作用：说明功能如何拆成模块，以及模块之间的依赖顺序。

建议包含：
- 文档地图
- 模块列表
- 模块依赖
- 设计顺序
- 开发顺序
- 当前待确认事项

不要把总览写成详细实现文档。

完成标准：新会话只读总览，也能知道应该先读哪些文档、先开发哪些模块、哪些模块不能提前动。

## 公共上下文

作用：提供所有模块都必须遵守的稳定上下文。

建议包含：
- 技术栈和版本
- 项目目录结构
- 包路径和命名约定
- 统一响应格式
- 基础实体或共享类型
- 数据库约定
- 鉴权和用户上下文
- 参考代码位置
- 全局异常处理

只放稳定约定。某个模块独有的内容放到模块文档。

## 模块详细设计

作用：让一个模块可以被 AI 按文档开发。

建议包含：
- 模块定位
- 前置依赖
- 上下游关系
- 文件结构
- 数据模型、DTO 或类型定义
- API 合约
- Service 关键逻辑
- 异常和边界情况
- 验收或验证方式

文档要足够具体，但不要机械复制最终代码的每一行。

完成标准：另一个 AI 会话读取公共上下文和该模块文档后，可以开始实现，并知道如何验证结果。

## 进度文档

作用：作为设计和开发阶段的状态机。

设计进度和开发进度要分开追踪。能解锁下一阶段的状态变更，需要用户确认。

推荐用“当前阻塞点/下一步动作”代替单纯的“当前阶段”，让进度文档能指导下一步工作。

## 复查文档

作用：开发前发现跨文档矛盾。

AI 应主动执行复查，输出问题汇总；用户负责确认每个问题的处理结论。

建议记录：
- 问题标题
- 影响文档和位置
- 严重程度
- 问题描述
- 建议修改
- 用户结论
- 最终状态
