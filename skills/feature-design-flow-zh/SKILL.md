# 需求设计流转

使用这个 skill，把一个还比较模糊的功能意图，整理成可以交给 AI 编码会话执行的设计文档体系。目标不是为了写厚文档，而是把共识、假设、边界、依赖、检查点和人工确认显式化。

## 资源定位

本文档中的 `references/...` 和 `assets/templates/...` 都是相对于 skill 根目录的路径，也就是和 `SKILL.md` 同级的目录。

执行时先确定当前 skill 根目录：

1. 如果系统提供了 skill 路径，直接以该路径作为根目录。
2. 如果只知道正在读取的 `SKILL.md`，以 `SKILL.md` 所在目录作为根目录。
3. 读取辅助文件时使用 `<skill根目录>/references/...`。
4. 复制模板时使用 `<skill根目录>/assets/templates/...`。

不要从项目工作目录直接猜测这些相对路径；项目文档输出目录和 skill 安装目录是两件事。

## 流程选择

先判断走轻量流程还是完整流程。

使用轻量流程，当功能满足以下多数条件：

- 只影响 1 到 2 个模块。
- 没有复杂数据模型或跨系统状态流转。
- 没有外部 API、支付、权限、审计、AI Tool/Prompt 等高风险边界。
- 用户只需要快速把想法整理成可实现设计。

轻量流程：

```text
需求文档 + QA 决策记录 -> 模块详细设计 -> 小型复查 -> 开发
```

使用完整流程，当功能满足任一条件：

- 涉及 3 个以上模块或前后端/多服务协作。
- 有数据库结构、鉴权、状态流转、异步任务或外部系统依赖。
- 有 AI Prompt、Tool Calling、模型行为约束等不稳定行为。
- 多人协作，或后续需要长期维护。
- 用户明确要求标准化设计文档流。

完整流程：

```text
功能想法 -> 需求文档 -> QA 决策记录 -> 拆分设计总览
-> 公共上下文 -> 模块详细设计 -> 进度门禁
-> 跨文档复查 -> 确认并修改 -> 开发阶段
```

## 核心原则

设计和开发分阶段处理。完整流程下，设计阶段没有完成、复查、确认之前，不进入实现。轻量流程下，也至少要保留需求、关键决策、模块设计和复查结论。

## 启动时先做什么

如果项目已有文档，先读取现有结构。优先查找：

- `docs/intention/`
- `docs/design/`
- `docs/requirements/`
- `docs/recheck/`
- `CLAUDE.md`
- 其他项目级规划文档

如果没有现成结构，按功能创建一个独立目录，例如：

```text
docs/<feature-name>/
├── 1-需求文档.md
├── 2-QA决策记录.md
├── 3-拆分设计总览.md
├── design/
│   ├── 00_公共上下文.md
│   ├── 01_<模块名>.md
│   ├── ...
│   └── PROGRESS.md
└── recheck/
    ├── REVIEW_TEMPLATE.md
    └── 设计文档问题汇总.md
```

命名可以按仓库已有习惯调整。

## 文档分工

保持每类文档职责单一：

- 需求文档：说明业务目标、功能范围、不做什么、用户流程、数据/API 预期、验收标准。
- QA 决策记录：记录讨论问题、取舍、最终决策、待确认事项，以及为什么这么定。
- 拆分设计总览：定义模块拆分、依赖关系、文档地图、设计顺序和开发顺序。
- 公共上下文：沉淀所有模块都需要遵守的稳定约定，例如技术栈、包结构、响应格式、数据库约定、鉴权方式、参考代码位置。
- 模块详细设计：围绕一个可实现模块，写清楚职责、依赖、路径、数据结构、接口、Service 逻辑、边界条件、验收点。
- 进度文档：作为阶段状态机，分别追踪设计阶段和开发阶段，避免提前开发。
- 复查文档：跨文档检查命名、字段、接口、依赖、Prompt/Tool 行为、状态流转等一致性问题。

需要更细的说明时，读取 `<skill根目录>/references/文档职责.md`。

## 设计流转步骤

1. 整理需求。
   - 提取目标、非目标、角色、核心流程、数据、接口、约束和验收标准。
   - 不确定内容要标记为假设或待确认，不要伪装成已确定结论。

2. 做 QA 澄清。
   - 把含糊点转成明确问题。
   - 对每个问题记录结论、理由、状态。
   - QA 状态值只使用：已确认、待确认、暂缓。

3. 拆分模块。
   - 按依赖顺序建立设计总览。
   - 模块边界应贴近代码结构、数据归属和实现责任。

4. 编写公共上下文。
   - 只放稳定的全局约定。
   - 不把某个模块独有的细节塞进公共上下文。

5. 编写模块详细设计。
   - 每个模块都先说明定位、依赖和当前状态。
   - 写到 AI 可以据此开发：路径、类/函数名、请求响应、表结构、服务步骤、异常边界、验收点。
   - 模块文档要尽量自包含，同时引用公共上下文和上游依赖。

6. 维护进度门禁。
   - 设计状态和开发状态分开。
   - 一个设计文档完成后，需要用户确认，才能标记完成。
   - 确认前用 Definition of Done 检查文档是否达到可开发粒度。
   - 确认后，要回查需求、QA、总览和相关模块文档，修正不一致再进入下一步。

7. 开发前主动复查。
   - AI 主动对比需求文档、QA 记录、总览、公共上下文、模块文档，并输出问题汇总。
   - 用户负责确认每个问题的处理结论：确认修改、暂不修改、待确认。
   - 只有已确认的问题被修改或明确暂缓后，才能进入开发阶段。

门禁细节见 `<skill根目录>/references/流转规则.md`，复查范围见 `<skill根目录>/references/复查清单.md`。

## Definition of Done

设计文档准备标记完成前，至少满足：

- 目标、范围、不做事项没有互相冲突。
- 关键 QA 问题都有状态，阻塞项没有被忽略。
- 模块依赖和开发顺序清楚。
- 涉及接口时，有方法、路径、请求示例、响应示例和错误边界。
- 涉及数据时，有字段、类型、必填、状态含义、索引或查询说明。
- 涉及业务逻辑时，Service 步骤覆盖主流程和至少一个异常/边界路径。
- 涉及 AI 行为时，Prompt/Tool 的触发条件、参数来源、返回处理清楚。
- 验收点可测试，不只是“功能正常”。
- 尚未解决的问题被标记为待确认或暂缓。

更完整的门禁清单见 `<skill根目录>/references/流转规则.md`。

## 人机协作规则

把人的确认视为流程的一部分，而不是额外打扰。

以下情况要请求用户确认：

- 需求范围变化。
- 模块边界或开发顺序变化。
- 数据模型、鉴权方式、API 合约、用户可见行为发生变化。
- 设计文档准备标记完成。
- 复查问题属于严重或中等，并且存在多种修复方案。
- 准备从设计阶段切换到开发阶段。

低风险的措辞、模板填充、文档排版，可以直接处理。

## 模板

创建新文档流时，使用 `<skill根目录>/assets/templates/` 下的模板：

- `需求文档.md`
- `QA决策记录.md`
- `拆分设计总览.md`
- `公共上下文.md`
- `模块详细设计.md`
- `PROGRESS.md`
- `REVIEW_TEMPLATE.md`

模板内带有“填写示例”。生成正式项目文档时，可以保留示例作为参考，也可以在填充完成后删除示例段，避免混入项目正文。
